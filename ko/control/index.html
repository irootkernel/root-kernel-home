AI-SPARK and Podway

AI-SPARK는 서버 개발에 필요한 spec을 검증하고, 사람이 승인한 명세에 따라 AI가 코드를 작성하도록 합니다. 실제 상태 전이는 FSM runtime이 제어합니다. Podway는 이 제어 원리를 일반 작업으로 확장해, 작업에 맞는 절차와 각 단계의 진행 조건을 미리 정합니다. AI는 허용된 범위에서 작업하고, 중요한 결정과 최종 승인은 사람이 맡습니다.

AI가 만든 코드를 검토하고 복구하는 일

AI가 만든 코드가 늘어날수록 사람이 확인해야 할 양도 늘어납니다. 코드가 의도대로 동작하는지 검토하고 적용을 승인하는 데는 여전히 시간과 판단이 필요합니다.

API 계약과 권한 정책, 상태 모델, 테스트가 서로 다른 버전을 기준으로 하면 이를 맞추기 위한 재작업이 필요합니다. 문제가 생겼을 때 돌아갈 단계와 다시 확인할 범위를 정해 두지 않으면 복구도 어려워집니다.

루트커널은 AI가 작업할 범위와 단계별 검증·승인 조건을 먼저 정합니다. 문제가 생겼을 때 돌아갈 경로도 절차에 포함해, 어떤 작업부터 다시 진행해야 하는지 확인할 수 있도록 합니다.

Spec이 구현의 경계를 정합니다

AI-SPARK는 인터페이스, 상태 모델, 연결 규칙, 권한 정책을 spec bundle로 묶어 함께 버전 관리합니다. AI는 검증을 통과하고 사람이 승인한 버전을 기준으로 코드를 작성합니다.

spec bundle에서 만든 revision key는 검증 결과와 승인 기록을 해당 명세 버전에 연결합니다. 구현과 배포도 같은 버전을 기준으로 진행하므로, 승인한 내용과 실제 작업 대상이 일치하는지 확인할 수 있습니다.

revision이 일치하고 필요한 산출물이 모두 갖춰졌을 때만 다음 단계로 진행할 수 있습니다. 확인되지 않은 상태에서는 진행을 허용하지 않는 fail-closed 원칙을 적용합니다.

  1. Spec revision
  2. Deterministic validation
  3. 사람 승인
  4. 구현·테스트
  5. 배포

Deterministic validation과 사람의 승인

AI-SPARK의 검증기는 같은 검증 조건에서 같은 spec bundle을 검사하면 같은 위반 목록을 반환합니다. 모델의 판단에 의존하지 않으므로, 동일한 조건으로 다시 검사해 결과를 확인할 수 있습니다.

검증 규칙은 검증받는 쪽에서 수정할 수 없도록 분리합니다. 사람의 승인은 검증을 통과한 명세 버전에 연결되며, 명세가 바뀌면 다시 검증하고 승인받아야 합니다.

FSM runtime이 상태 전이를 제어합니다

승인 후 AI는 이벤트 발생과 전이 조건, 전이 동작에 필요한 코드를 작성합니다. 실제 상태 전이와 동시성 제어는 FSM runtime이 맡아, 선언된 규칙에 따라 상태를 바꾸고 그 내역을 기록합니다.

허용되지 않은 이벤트는 거부합니다. 문제가 생기면 Reverse Map을 활용해 실패한 요청과 서버 로그를 관련 연산, 권한 정책, 상태 전이까지 되짚습니다. 실행 기록에는 명세 버전과 실행을 식별할 정보를 함께 남겨, 문제가 발생한 맥락을 확인할 수 있도록 합니다.

AI-SPARK의 핵심 발명은 국내 특허로 출원했습니다.

Podway는 작업에 맞는 절차로 AI의 실행을 제어합니다

Podway는 에이전트의 할 일 목록과 함께 작업 절차를 관리합니다. 작업을 절차 그래프로 구성해 각 단계의 진행 조건과 재작업 경로를 미리 정합니다. 문제가 생겨 이전 단계로 돌아가면, 절차에 따라 기존 기록의 유효성을 관리하고 다시 수행해야 할 작업과 검증을 확인할 수 있습니다.
