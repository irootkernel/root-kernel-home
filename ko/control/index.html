AI-SPARK and Podway

AI-SPARK는 spec bundle, deterministic validation, 사람의 승인, FSM runtime으로 서버 개발의 실행 경계를 정합니다. Podway는 같은 원리를 workflow로 넓혀 작업마다 절차를 세션 전에 정하고 검사합니다. 두 기술 모두 AI가 허용된 state transition 안에서 일하게 하고 최종 권한은 사람에게 남깁니다.

생성 뒤의 병목

AI는 짧은 시간에 많은 코드를 만들 수 있습니다. 사람이 검토하고 승인할 수 있는 속도는 그만큼 빨라지지 않았습니다.

API 계약, 권한 정책, 상태 모델, 테스트가 서로 다른 revision을 가리키면 생성 속도는 재작업을 늘립니다. 실패 뒤 어디로 돌아가야 하는지 정해 두지 않으면 복구할 때도 같은 문제가 반복됩니다.

그래서 Root Kernel은 모델 성능보다 실행 경계를 먼저 다룹니다. 무엇을 만들 수 있고, 어떤 검증과 승인을 통과해야 하며, 실패하면 어느 상태로 돌아가는지를 구조로 정합니다.

Spec이 구현의 경계를 정합니다

AI-SPARK에서는 구현보다 spec이 먼저입니다. 검증되고 승인된 revision만 구현의 입력이 됩니다.

spec bundle에서 만든 revision key는 검증 결과, 승인 기록, 구현, 배포를 하나의 흐름으로 묶습니다. 서로 다른 revision이 섞이거나 필수 산출물이 빠지면 다음 단계는 fail-closed로 멈춥니다.

spec bundle에는 인터페이스, 상태 모델, 연결 규칙, 권한 정책이 함께 들어갑니다. 구현이 따라야 할 계약을 하나의 revision으로 고정하므로 각 요소가 따로 바뀌지 않습니다.

  1. Spec revision
  2. Deterministic validation
  3. 사람 승인
  4. 구현·테스트
  5. 배포

Deterministic validation과 사람의 승인

검증기는 같은 spec bundle에 대해 같은 위반 목록을 냅니다. 결과가 모델의 판단이나 실행 순서에 따라 달라지지 않습니다.

검증 규칙은 생성된 코드와 분리되어 있고, 승인은 검증을 통과한 revision에 묶입니다. 내용이 바뀌면 이전 승인을 재사용할 수 없습니다.

Mutation Harness는 spec에 의도적으로 결함을 넣고 검증기가 그 결함을 잡는지 확인합니다. 결함이 있는 spec을 통과시키면 그 사례를 검증기의 결함으로 기록합니다.

FSM runtime이 state transition을 통제합니다

승인 뒤 AI가 작성하는 구현 코드는 이벤트, 전이 조건, 전이 동작에 집중합니다. 실제 state transition과 동시성 제어, 전이 기록은 FSM runtime이 맡습니다.

허용되지 않은 이벤트는 거부 경로로 보내고, ReverseMap은 서버 로그를 연산과 정책, state transition으로 되짚어 줍니다. RunIdentity는 실행 기록이 어느 revision과 실행을 가리키는지 고정합니다.

AI-SPARK의 핵심 발명은 국내 특허로 출원했습니다.

Podway는 작업마다 절차를 정하고 검사합니다

Podway는 AI-SPARK의 제어 원리를 workflow로 확장하며 모든 변경에 선행 조건과 idempotency key를 요구합니다. 한 Git worktree에는 한 작업만 두고, 사람과 에이전트는 같은 공개 계약으로 허용된 다음 행동을 수행합니다.

작업에 맞는 절차는 세션 전에 선택하거나 구성합니다. Podway는 도달 가능성과 종료 가능성을 검사해 잘못된 절차를 거절하고, 허용된 절차의 다이제스트를 고정해 실행 중 바뀌지 않게 합니다.

실행 중에는 미리 선언된 행동, 판단, 재시도, 재작업 경로만 사용할 수 있고, 되돌아갈 때 무효가 되는 증거도 절차가 정합니다. `podway observe`가 현재 상태와 `allowed_actions`를 보여주면 사람이나 에이전트가 무엇을 할지 고릅니다. Podway는 작업을 수행하거나 기록의 의미가 참인지 검증하지 않습니다.
