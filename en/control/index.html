AI-SPARK and Podway

AI-SPARK sets execution boundaries for server development through a spec bundle, deterministic validation, human approval, and an FSM runtime. Podway extends the same principles to workflows by selecting or configuring and checking a Procedure v2 for each task before a session starts. Both technologies keep AI within allowed state transitions while leaving final authority with people.

The bottleneck after generation

AI can produce large volumes of code quickly. Human review and approval have not accelerated at the same rate.

When API contracts, authorization policies, state models, and tests point to different revisions, faster generation creates more rework. The same failure recurs during recovery unless the return path is defined in advance.

Root Kernel therefore starts with execution boundaries rather than model capability: what may be built, which validation and approval it must pass, and which state receives the work after failure.

Specifications define the implementation boundary

In AI-SPARK, the specification comes before implementation. Only a validated and approved revision becomes an implementation input.

A revision key derived from the spec bundle binds validation results, approval records, implementation, and deployment into one chain. If revisions are mixed or a required artifact is missing, the next stage stops fail-closed.

The spec bundle carries the interface, state model, bindings, and authorization policy together. It fixes the implementation contract to one revision so the elements cannot drift independently.

Deterministic validation and human approval

The validator returns the same violation list for the same spec bundle. Its result does not depend on model judgment or execution order.

Validation rules are independent of generated code, and approval is bound to the revision that passed them. Once the content changes, the previous approval cannot be reused.

Mutation Harness deliberately corrupts a specification and checks whether the validator detects the defect. If the corrupted specification passes, the miss is recorded as a validator defect.

The FSM runtime controls state transitions

After approval, AI-written implementation code focuses on events, guards, and actions. The FSM runtime owns the actual state transitions, concurrency control, and transition logging.

Disallowed events follow a reject path. ReverseMap traces server logs back to the operation, policy, and state transition, while RunIdentity fixes which revision and run each record belongs to.

Podway defines and checks a procedure for each task

Podway extends AI-SPARK's control principles to workflows and requires a precondition and idempotency key for every mutation. One Git worktree holds one task, and people and agents use the same public contract to take allowed next actions.

A Procedure v2 is selected or configured for the task before the session begins. Podway checks reachability and termination, rejects an invalid procedure, and stores the admitted procedure as a digest-pinned immutable snapshot.

During execution, only declared actions, decisions, retries, and rework paths are available, and the procedure defines which evidence is invalidated on return. `podway observe` reports current state and `allowed_actions`; a person or agent chooses what to do next. Podway neither performs the work nor verifies the semantic truth of the record.
